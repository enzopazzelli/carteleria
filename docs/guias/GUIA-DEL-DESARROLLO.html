1El proyecto en cinco minutos

Qué problema resuelve, para quién y cómo está pensado.

Un sistema a medida para una empresa de cartelería de gran formato en chapa. Reemplaza tres tareas manuales: cotizar un cartel, acomodar sus piezas en la chapa (nesting) y hacer aprobar el presupuesto antes de que llegue al cliente. Entra un dibujo DXF exportado de CorelDRAW y sale un presupuesto con precio sugerido, un PDF para el cliente y archivos de corte para el taller.

Backend

Python 3.11+, FastAPI, SQLAlchemy 2, Alembic. Geometría con shapely y ezdxf. Anidado con Sparrow (spyrrow).

Frontend

React 18, Vite, TypeScript, Tailwind, React Query. Sin lógica de negocio: pide todo al servidor.

Datos

SQLite en desarrollo, PostgreSQL en el servidor. Los DXF se guardan como archivos junto a la base.

Estado

Funciona de punta a punta en local, con login. Falta el despliegue (Docker, copias, PostgreSQL, servidor).

Qué guía leer

Esta es la guía para quien desarrolla. Si necesitás entender cómo lo usa la gente de la empresa, está la guía del usuario. El mapa de todos los documentos del repositorio está en la sección 14.

Principios de diseño

  • El servidor sabe, la pantalla pide. Toda regla de negocio vive en el backend; el frontend solo muestra y envía.
  • Un solo lugar para cada decisión. Si una regla se repite en dos sitios, se unifica (ejemplo: anidado_que_cuenta.py decide qué anidado cuenta para el precio, y costeo, inicio, PDF y Chapas lo consumen).
  • Nada hardcodeado. Los valores configurables tienen un ID en el registro de supuestos (ver sección 11).
  • Los errores los lee una persona. Los mensajes están pensados para quien usa el sistema, no para quien programa.

2Arquitectura

Qué procesos hay y cómo se hablan.

Navegador — SPA de React. Habla con un solo origen: /api/…. La cookie de sesión viaja sola.
Vite (desarrollo) / Caddy (producción, planeado) — reenvía /api/* al servidor sacando el prefijo. Las rutas del backend no llevan /api.
Servidor — FastAPI + Uvicorn, puerto 8000. Rutas en app/api/, lógica en app/services/, tablas en app/modelos/.
Base de datos
SQLite (backend/local/carteleria.db) o PostgreSQL, vía DATABASE_URL.
Archivos
El DXF subido de cada trabajo, en local/archivos/: se conserva para poder releerlo con otra escala.
Sparrow
Proceso aparte (sparrow_worker.py), lanzado y vigilado por el servidor. Tarda; el servidor sigue respondiendo.
PDF
ReportLab, dentro del propio servidor.

Un pedido, de punta a punta

  1. La pantalla llama a una función de src/api/*.ts (por ejemplo subirDxf), que hace el fetch a /api/….
  2. Vite (o Caddy) reenvía el pedido al backend sin el prefijo.
  3. La ruta en app/api/rutas_*.py valida el pedido con un esquema de Pydantic (esquemas_*.py) y comprueba la sesión y los permisos.
  4. La ruta llama a un servicio en app/services/…, que trabaja con los modelos de app/modelos/ (SQLAlchemy) y con las librerías geométricas.
  5. Si algo falla de una manera que el usuario puede entender, se lanza ErrorParaElUsuario; el manejador lo convierte en JSON con un mensaje (y un detalle técnico aparte).
  6. La respuesta vuelve a la pantalla; React Query actualiza o invalida lo que corresponda.

Cola de trabajos largos

El anidado puede tardar minutos. Se lanza en segundo plano (app/cola/, configurable con CARTELERIA_COLA: proceso por defecto, celery cuando exista) y la pantalla consulta el progreso (progreso.py), con tiempo máximo y botón de cancelar. Se pueden correr varios a la vez. Los archivos de trabajo temporales van a local/tmp/ (no a la carpeta temporal del sistema, que suele estar en un disco chico) y se borran al terminar.

3Puesta en marcha

De cero a la app corriendo en tu máquina, sin Docker ni bases externas.

Qué necesitás

Vas a usar tres terminales. Los comandos son de Windows; en Mac/Linux cambiá .venv\Scripts\python por .venv/bin/python.

git clone https://github.com/enzopazzelli/carteleria.git
cd carteleria

Terminal 1 — el servidor (queda corriendo)

cd backend
python -m venv .venv
.venv\Scripts\python -m pip install -r requirements-dev.txt
.venv\Scripts\python -m uvicorn app.api.app:app --reload

La base se crea o se actualiza sola al arrancar (app/arranque.py): si estaba atrasada, antes deja un respaldo en backend/local/respaldo-<fecha>-antes-de-<versión>/. Si la base es más nueva que el código (pasa al volver a una rama vieja), no la toca y el servidor no arranca. Cuando termina, http://localhost:8000/docs muestra la documentación interactiva de la API (en producción está cerrada).

Una sola vez, el primer usuario (sin él la pantalla no deja entrar), con el servidor ya arrancado:

.venv\Scripts\python -m app.usuarios crear enzo --nombre "Enzo" --administrador --puede-aprobar --generar

Imprime una contraseña temporal; al entrar, la pantalla pide elegir una propia (mínimo 10 caracteres).

Terminal 2 — datos de demostración

cd backend
.venv\Scripts\python scripts/cargar_catalogo_demo.py
.venv\Scripts\python scripts/generar_dxf_demo.py

Cargan materiales «DEMO» con precios inventados (marcados «(simulado)») y crean backend/local/demo.dxf. Se pueden repetir sin duplicar nada.

Terminal 3 — la pantalla (queda corriendo)

cd frontend
npm ci
npm run dev
Abrí exactamente esta dirección

Abrí http://localhost:5173, no 127.0.0.1 ni otro puerto. Vite tiene strictPort: si el 5173 está ocupado, no arranca (antes se corría solo al 5174 y la app cargaba pero nada funcionaba). Lo mismo con el 8000.

5El backend por dentro

Capas, módulos y las reglas de cada una.

Capas

api → services → modelos. Una ruta solo valida, comprueba permisos y delega; no contiene lógica de negocio. Un servicio no conoce FastAPI. Los modelos solo describen tablas.

Servicios (app/services/)

CarpetaQué hace
ingesta/Lee el DXF: dxf.py (parser), dibujo.py (la imagen de «cómo se leyó»), uniones.py, analisis.py (qué es pieza, agujero, descartada), correcciones_guardadas.py (recordar correcciones por contenido del archivo).
nesting/El anidado. sparrow.py + sparrow_worker.py (motor principal), engine.py (rectangular, de prueba), huecos_primero.py, reacomodar.py, mover_entre_chapas.py, material_usado.py, exportacion_dxf.py, pdf_anidado.py, visualizacion.py.
seccionado/grilla.py: parte una pieza que no entra en una chapa en tramos, buscando la mejor grilla (ángulo y desplazamiento).
piezas/Alta y consulta de piezas de un trabajo.
catalogo/Materiales, medidas, artículos y precios; planilla.py y revision.py (leer el Excel y mostrar qué cambiaría), aplicar.py, retazos.py.
presupuesto/totales.py y sugerido.py (costeo y precio), estados.py (máquina de estados), pdf.py y documento.py (PDF del cliente), empresa.py (logo y datos), del_catalogo.py.
usuarios/Alta, baja, contraseñas (argon2id), sesiones y bloqueo.

Módulos sueltos en app/: config.py (configuración), arranque.py (migra y respalda al iniciar), mensajes.py (ErrorParaElUsuario), anidado_que_cuenta.py, costeo.py, pasos.py, progreso.py, registro.py (logs rotativos), usuarios.py (el comando de emergencia).

Modelos (tablas)

Las medidas se guardan con el tipo Milimetros (modelos/tipos.py), un Decimal con precisión fija. Hay una carpeta de migraciones con una por cambio de esquema.

Autenticación y permisos

  • Sesión por cookie, contraseñas con argon2id. Duración, bloqueo y largo mínimo, configurables (sección 3).
  • Los pedidos que cambian algo (todo lo que no es GET) deben llevar el encabezado X-Cartel-Pedido. Sin él, el servidor los rechaza. Es la defensa contra pedidos forjados desde otro sitio; el cliente del frontend (src/api/client.ts) lo agrega solo.
  • Dos permisos: puede_aprobar y administra_usuarios. Se exigen con Depends(exigir_permiso("…")).
  • Toda ruta nueva exige sesión. El test test_todas_las_rutas_exigen_sesion recorre las rutas y falla si alguna queda abierta. Si agregás una pública a propósito, tenés que declararla.
  • Siempre tiene que haber al menos una persona que administre usuarios; el servicio lo garantiza.

Errores para personas

Todo error que lee una persona se lanza con ErrorParaElUsuario(mensaje, detalle=…). Reglas (también en CONVENCIONES.md §6):

  1. Primero qué pasó, después qué hacer. Una o dos oraciones, con voseo («elegí», «probá»).
  2. Se nombra lo que el usuario ve: la pieza por su nombre del dibujo, el grupo por su nombre, la chapa por material y medida.
  3. Nunca ids de base, códigos del proyecto (CART-, PAR-), nombres de programas (Sparrow, rectpack), inglés ni palabras de programación.
  4. Lo técnico va en detalle; la pantalla lo muestra en «Ver detalle técnico».

Un cálculo que solo conoce ids lanza un error con nombre propio y api/traducir_errores.py lo traduce. tests/test_mensajes_claros.py revisa los textos.

6El dominio, por temas

Las ideas que hay que entender antes de tocar cada parte.

DXF y la escala

  • El parser (ingesta/dxf.py) arma piezas cerradas a partir de entidades del DXF. No lee texto, imágenes ni HATCH; cuenta lo que ignora y lo avisa. Los contornos que no cierran (empalmes con huecos de más de 0,1 mm) se informan aparte.
  • La escala (escala_a_mm) es los mm por unidad del dibujo. Nunca se adivina: las cabeceras del DXF (INSUNITS) no son confiables (se vieron valores 4, 5 y 6 para dibujos equivalentes). La pantalla la pide y da una referencia: POST /dxf/medida mide el dibujo en sus unidades y la pantalla multiplica por la escala escrita («con esta escala el dibujo mide … mm»).
  • Hay dos pasos: …/dxf/lectura (cómo se leería, sin guardar nada) y …/dxf (cargar). Las correcciones manuales (forma «no va», descartar) se recuerdan por el contenido del archivo.

Anidado

  • Sparrow (spyrrow) es el motor principal; corre en un proceso aparte. Soporta giro libre, huecos (usar_anidado_en_huecos) y varios anidados a la vez. rectpack queda como motor rectangular de prueba.
  • «Entra en la chapa» es una sola regla (sparrow.entra_en_la_chapa), con los mismos giros que el anidado: con giro libre, a cualquier ángulo (de a 1°); con veta, media vuelta; si no, cuartos de vuelta.
  • Cada ejecución (EjecucionNesting) guarda parámetros y colocaciones; recalcular crea una nueva y la anterior queda en el historial.
  • El material usado se mide en ancho × alto (sobrante arriba). El sobrante de una chapa puede guardarse como retazo (Formato.es_retazo), que dice de dónde salió y su estado.
  • Al mover una pieza a otra chapa (mover_entre_chapas.py), si no entra en lo libre, se reacomoda esa chapa con Sparrow (reacomodar.py), con «Deshacer».

Seccionado

Una pieza que no entra en ninguna chapa se parte en tramos con una grilla (ángulo + desplazamiento), buscando la que da menos tramos y menos soldadura. Los tramos son Pieza con seccionada_de_id; la original queda descartada. Hay un tope de tramos (CARTELERIA_TOPE_TRAMOS) y se rechaza antes de buscar lo que ya se sabe que no lo cumple. Aplicar reemplaza los tramos anteriores, salvo que estén en un anidado guardado.

Costeo y presupuesto

  • Dinero siempre en Decimal, nunca float; el redondeo se aplica una sola vez, al final.
  • El costeo (costeo.py, presupuesto/totales.py) suma material usado (del anidado), artículos del catálogo, mano de obra, IVA y margen; sugerido.py calcula el precio con el margen configurado.
  • Regla única del anidado: anidado_que_cuenta.py decide qué anidado de un grupo cuenta. Si cambia la chapa del grupo después de anidar, ninguno lo da por terminado ni lo cobra. Hay una prueba «guardiana» (test_regla_unica_del_anidado.py) que impide reintroducir una segunda regla.
  • El PDF del cliente no muestra costos ni márgenes; el logo y los datos de contacto vienen de backend/local/empresa/ (fuera de git). Sin esa carpeta, el PDF sale sin logo.

Cada carga se guarda (CargaDePlanilla) con sus cambios de precio (CambioDePrecio).

7El frontend por dentro

Cómo está organizada la pantalla y qué patrones se repiten.

Patrón: api → hooks → routes

  1. src/api/xxx.ts: una función por llamada al servidor, con sus tipos. Cada archivo tiene su xxx.test.ts.
  2. src/hooks/useXxx.ts: envuelve esas funciones con React Query (useQuery / useMutation).
  3. src/routes/*.tsx: las pantallas. Las del espacio de trabajo están en routes/TrabajoWorkspace/: PiezasTab, GruposTab, AnidadoTab, ChapasTab, CosteoTab.

Lógica pura en archivos .ts aparte

Lo que se puede calcular sin React (formatear importes, armar filas de una comparación, decidir si una pieza se puede seccionar, la referencia de la escala) vive en archivos .ts junto a la pantalla, con su .test.ts. Así se prueba sin montar componentes (el entorno de Vitest es node).

Invalidar lo que cambió

Cuando una acción modifica datos, se invalidan las consultas afectadas. Por ejemplo, refrescarPiezasYDisenio (hooks/usePiezas.ts) refresca piezas, diseño, «a seccionar», ejecuciones y costeo de un trabajo. Si agregás una consulta que depende de las piezas, sumala ahí o la pantalla mostrará datos viejos.

Sesión y rutas protegidas

auth/SesionContext guarda quién entró; RutaProtegida manda a la pantalla de entrada si no hay sesión y fuerza «Mi cuenta» si la contraseña es temporal. Barra.tsx muestra «Usuarios» solo a quien administra.

8Base de datos y migraciones

Alembic, SQLite y PostgreSQL.

  • Una migración por PR, generada justo antes de abrirlo (después de git pull --rebase origin main), para que su cabeza sea la última.
  • Se revisa siempre el archivo generado: el autogenerate se equivoca con índices, defaults y renombres.
  • downgrade() funcional siempre. Migración de datos ≠ migración de esquema: van separadas.
  • Si quedan dos heads (alembic heads): primero hablarlo; después alembic merge.
  • Las migraciones se escriben para SQLite y se verifican también contra PostgreSQL 16 en el CI (aplicar todo, deshacer, guardar y leer datos del modelo).
cd backend
alembic upgrade head                                  # aplicar (el servidor ya lo hace al arrancar)
alembic revision --autogenerate -m "agregar tabla x"  # generar
alembic heads                                         # ver cabezas
Antes de migrar la base real

El servidor deja solo un respaldo cuando actualiza la base al arrancar. Aun así, antes de un cambio de esquema grande conviene copiar backend/local/carteleria.db.

Probar sin tocar tus datos

scripts/copiar_base.py arma una copia de la base en local/copias/<nombre> y se corre la app contra ella con CARTELERIA_DATOS=local/copias/<nombre>. Ojo: la copia puede seguir apuntando a los DXF reales por ruta absoluta.

Qué se corre, cuándo, y qué es obligatorio.

Si el disco del sistema está lleno

«database or disk is full» en las pruebas suele ser la carpeta temporal del sistema. Corré con --basetemp apuntando a otro disco, y con CARTELERIA_DATOS en otro lado.

Obligatorias

No todo necesita test, pero tres cosas sí, sin excepción: el motor de nesting (un error se ve como chapa mal cortada), el motor de costeo (un error llega al cliente como un precio equivocado) y la máquina de estados (una transición inválida rompe el circuito de aprobación).

Pruebas guardianas

Varias pruebas existen para que una regla no se rompa en silencio: todas las rutas exigen sesión; una sola regla de qué anidado cuenta; los mensajes al usuario respetan las reglas de redacción. Si una falla, no la «arregles» debilitando la prueba: la falla te está diciendo que rompiste una regla del proyecto.

CI (GitHub Actions, .github/workflows/ci.yml)

Corre en cada push a main, en cada PR y a mano (workflow_dispatch). Dos trabajos:

  • backend: Python 3.11, alembic upgrade head contra una base vacía (las migraciones tienen que correr de cero) y pytest -q completo, sobre SQLite.
  • postgres: un PostgreSQL 16 de verdad; aplica y deshace las migraciones y prueba el modelo.

CI en verde es innegociable para fusionar. El CI es también donde se verifica lo que no se puede probar en la máquina de quien desarrolla (por ejemplo, Docker).

10Flujo de trabajo con Git

Ramas, commits y PR.

  1. Código: una rama corta (feat/…, fix/…, chore/…) desde main, actualizada con git pull --rebase origin main.
  2. PR a main con título claro, qué cambia y cómo probarlo. Si el diff pasa unas 400 líneas, partirlo.
  3. CI en verde, revisión del dueño de la zona y fusión; la rama se borra al fusionar.
  4. Documentación: puede ir directo a main, sin PR.

Commits: Conventional Commits, en español e imperativo: feat(piezas): referencia para la escala del DXF. Tipos: feat, fix, refactor, test, docs, chore, perf. El cuerpo explica el por qué, no el qué.

Sin Co-Authored-By

Los commits y las descripciones de PR van firmados solo por el autor humano: nada de trailers de atribución a herramientas o asistentes. Es una regla explícita del proyecto.

11Las reglas que no se negocian

Si te llevás solo esto de la guía, que sea esto.

1. No hardcode

Ningún valor configurable va escrito en la lógica ni repetido en dos documentos. Todo valor por defecto tiene un ID PAR-xx en docs/REGISTRO.md; el resto lo referencia por ID. Igual para supuestos (SUP-xx) y dudas (P-xx).

2. Todo en milímetros

Toda medida geométrica en mm y toda área en mm²; la unidad va en el nombre (ancho_mm, area_mm2). Convertir a m² solo al presentar. Una unidad equivocada da un presupuesto equivocado que nadie nota hasta que llega la chapa cortada.

3. Se documenta al avanzar

Una entrada en docs/BITACORA.md al cerrar cada jornada y el registro al día. Un registro desactualizado es peor que no tenerlo: da confianza falsa.

Otras convenciones

  • Dinero: Decimal, moneda explícita, redondeo una sola vez al final.
  • Idioma: el dominio en español (presupuesto, pieza, anidado); términos técnicos sin traducción natural en inglés (nesting, kerf); tablas y columnas en español snake_case; comentarios y documentación en español. Sin ñ ni acentos en identificadores de base ni en nombres de archivo.
  • Mensajes al usuario: ver sección 5.
  • Secretos: nunca en el repositorio (es público).

13Recetas: cómo agregar cosas

Los cambios más comunes, paso a paso.

Agregar una ruta nueva al backend
  1. Esquemas en app/api/esquemas_*.py (Pydantic).
  2. La lógica, en un servicio de app/services/… (la ruta solo delega).
  3. La ruta en el rutas_*.py que corresponda. La sesión se exige sola; si hace falta un permiso, Depends(exigir_permiso("…")).
  4. Errores para personas con ErrorParaElUsuario.
  5. Un test en tests/api/. El test guardián test_todas_las_rutas_exigen_sesion tiene que seguir pasando.
Agregar o cambiar una columna
  1. Cambiá el modelo en app/modelos/.
  2. git pull --rebase origin main y recién ahí alembic revision --autogenerate -m "…".
  3. Revisá el archivo a mano y asegurate de que downgrade() funcione.
  4. Si hay datos que transformar, hacelo en una migración aparte.
  5. Corré la suite completa. El job de PostgreSQL del CI la va a verificar también contra PostgreSQL.
Agregar un parámetro configurable
  1. Dale un ID PAR-xx en docs/REGISTRO.md §2, con su valor y su porqué.
  2. Léelo en app/config.py (con variable de entorno y valor por defecto), no en la lógica.
  3. En código y documentos, referencialo por ID; no repitas el valor.
Agregar una pantalla o una llamada al servidor
  1. La función en src/api/xxx.ts (+ su test) y el hook en src/hooks/.
  2. La pantalla en src/routes/; la lógica que no es de React, en un .ts aparte con test.
  3. Si cambia datos, invalidá las consultas afectadas.
  4. Usá los colores y tipografías de Tailwind por nombre; no escribas códigos de color a mano.
  5. Corré npm test y npx tsc -b.
Tocar el lector de DXF o el anidado
  1. Antes y después, corré scripts/lectura_del_corpus.py y comparalas: un cambio «inofensivo» puede empeorar el aprovechamiento o romper un dibujo real.
  2. Agregá un test con el caso que motivó el cambio.
  3. Anotá lo medido en la bitácora o en el documento del sub-proyecto.
Cerrar una jornada
  1. Entrada en docs/BITACORA.md (las más nuevas, arriba): qué se hizo, qué se decidió, qué queda.
  2. Actualizar docs/REGISTRO.md si se abrió o cerró algún ID, y docs/MAPA-DEL-PROYECTO.md si cambió el estado de una feature.

15Despliegue (lo que viene)

Hoy todo corre en local. Este es el plan para el servidor.

El plan detallado está en docs/plan/1.1-servidor-y-login/ (diseno.md y plan.md). La parte de login ya está hecha; sigue la entrega A3:

  1. Docker Compose: que todo levante con un comando, igual que en el servidor.
  2. Copias de seguridad diarias (con restic), y un aviso en /salud («backup atrasado») si pasan demasiadas horas sin una copia buena (CARTELERIA_BACKUP_HORAS_MAXIMAS).
  3. Catálogo a PostgreSQL: pasar los datos reales de SQLite.
  4. El servidor real: alquilarlo, dominio y HTTPS con Caddy (que además reenvía /api como lo hace hoy Vite).
Lo que se verifica en el CI

La máquina de desarrollo no tiene Docker: lo que depende de Docker o de PostgreSQL se verifica en GitHub Actions. Por eso el CI ya tiene un job con PostgreSQL 16.

Después: mail real y aviso al dueño, envío al cliente con el presupuesto congelado, WhatsApp, dashboard rápido y fotomontaje (OpenCV y Pillow).

16Llevar esto a otro proyecto

Las prácticas de este proyecto que sirven en cualquier otro.

Un registro central

Supuestos, parámetros y dudas con un ID, en un único documento. Código y documentos referencian el ID, nunca el valor.

Guardianes

Pruebas que protegen una regla (todas las rutas piden sesión, una sola regla de qué cuenta) y no solo un resultado.

Mensajes pensados

Primero qué pasó, después qué hacer; lo técnico aparte. Se revisa con una prueba.

Documentación por estado

Lo vigente, lo que sigue y lo histórico en carpetas distintas; nada suelto.

Migraciones sin sorpresas

Una por PR, generada al final, con downgrade, probada de cero y contra la base de producción en el CI.

Medir antes de cambiar

Un corpus de casos reales y un script que compara antes y después. Los cambios de «motor» se juzgan por números.

Aislar las pruebas

Una variable de entorno apunta toda la app a otra carpeta de datos: se prueba sin poner en riesgo la base real.

Todo en una unidad

Un solo sistema de unidades en el dominio, con la unidad en el nombre de cada variable.

Para reutilizar el esqueleto en otro proyecto: copiá la estructura de docs/ y CONVENCIONES.md, el patrón api → hooks → routes del frontend, la capa api → services → modelos del backend, y el CI de dos trabajos (suite rápida + base real).
